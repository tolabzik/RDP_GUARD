# Наблюдение за RDP через nginx stream

Это исследовательский прототип в отдельной ветке. Он не входит в выпущенный
установщик, не меняет действующий алгоритм Guard и не создаёт блокировок.

## Задача

Обычный TCP-прокси создаёт новое соединение к Windows. Windows Firewall видит
адрес прокси; бан этого адреса затрагивает всех клиентов, проходящих через него.
Предлагаемый адаптер переносит применение решения на входной Linux-сервер.
Windows остаётся источником сведений об отказах аутентификации.

Проверяемая цепочка:

```text
RdpCoreTS 140 (отказ)
  -> ActivityID + Windows-хост
RdpCoreTS 131 (TCP-подключение, IP:port)
  -> точные original/reply tuples conntrack
исходящий сокет nginx
  -> PID + номер соединения + экземпляр процесса
входящий сокет nginx / исходный IP клиента
```

Временные метки используются для проверки согласованности уже найденной связи.
Выбор ближайшего по времени соединения не допускается. Совпадение порта до и
после Docker MASQUERADE не предполагается: требуется фактическая запись NAT.

## Инструменты ветки

- `scripts/Export-ProxyEvidence.ps1` читает события 131/140 за явный UTC-интервал.
  Сохраняет исходный XML, provider, версию, компьютер, Record ID, ActivityID и поля.
  Предшествующие 131 можно включить через `-LookbackSeconds`.
- `scripts/Capture-ProxyEvidence.py` на Linux читает новые строки указанного
  nginx INFO-журнала и conntrack через netlink. Он не меняет настройки ядра,
  Docker, firewall или nginx. Длительность ограничена 300 секундами.
- `scripts/Save-ProxyEvidenceCache.ps1` временно сохраняет перекрывающиеся
  Windows-выгрузки каждые 10 секунд. По умолчанию работает 480 секунд,
  затем завершается. Использует новый каталог и не меняет настройки журнала.
- `python -m rdp_guard.proxy_evidence` сопоставляет два файла локально.
  Результат `demonstrated_candidate` означает наблюдаемое соответствие в
  предоставленных данных; это не разрешение на блокировку.

Пустая выгрузка Windows сама по себе не подтверждает отсутствие отказов.
Поле `assessment.status` отчёта различает недостаток Windows-событий,
неполные данные, отсутствие сопоставлений, частичное и полное сопоставление
предоставленных отказов. Во всех случаях исполнение блокировок отключено.

Пример Linux-сбора (адрес сервера назначения — документационный пример):

```sh
sudo python3 scripts/Capture-ProxyEvidence.py \
  --nginx-log /path/to/rdp-stream-info.log \
  --backend-ip 192.0.2.20 --backend-port 45451 \
  --listener-ip 0.0.0.0 --listener-port 45451 \
  --nginx-utc-offset-minutes 0 --duration 120 \
  --output /root/rdp-proxy-linux.jsonl
```

Журнал должен уже существовать и содержать INFO-события именно исследуемого
stream. UTC-смещение задаётся по часовому поясу nginx, в контейнере оно может
отличаться от хоста. Сбор начинается с текущего конца файла; нужны новые
соединения, открытые после запуска сборщика. Менять журналирование нужно
отдельно, с проверкой конфигурации и возможностью восстановления.

Для контейнера можно явно передать `--nginx-pid-namespace 'pid:[…]'`, взяв
значение из `/proc/<host-pid-nginx>/ns/pid`. При нескольких пространствах PID
явный выбор обязателен. Штатное завершение старых workers после graceful reload
записывается в снимки процессов; повторное использование PID другим процессом
прерывает сбор. Опрос раз в секунду может пропустить короткоживущий процесс —
это ограничение диагностического захвата, а не гарантия непрерывного учёта.

После окончания выбранного интервала на Windows, из повышенного PowerShell 5.1:

```powershell
powershell.exe -NoProfile -File .\scripts\Export-ProxyEvidence.ps1 `
  -StartUtc '2026-11-23T17:00:00Z' -EndUtc '2026-11-23T17:02:00Z' `
  -LookbackSeconds 30 -OutputPath .\rdp-proxy-windows.json
```

Время в примере нужно заменить интервалом внутри фактического Linux-сбора.
Граница окончания не включается. Существующий выходной файл не перезаписывается.
Интервал с окончанием в будущем отклоняется до чтения журнала.
При превышении лимита событий или ошибке чтения экспорт сохраняет признак
неполноты и возвращает код 2. Linux-сбор также возвращает код 2 при обнаруженном
пропуске. Отсутствие обнаруженных пропусков не доказывает полноту журналов ОС.

Windows-экспорт также содержит `log_coverage`: границы журнала до и после
чтения, размер, режим и оценку сохранности запрошенного диапазона. `complete`
описывает завершение запроса и преобразования; для сопоставления дополнительно
нужно `log_coverage.status=retained`. Старые выгрузки без этой проверки не
подтверждают сохранность истории.

Если история хранится меньше времени, чем занимает ручная выгрузка, сначала
запустите временный буфер в отдельном PowerShell или через `Start-Job`:

```powershell
.\scripts\Save-ProxyEvidenceCache.ps1 `
  -ExporterPath .\scripts\Export-ProxyEvidence.ps1 `
  -OutputDirectory C:\Temp\rdp-proxy-cache-new -DurationSeconds 480
```

Дождитесь `ready=true` в `status.json`, затем выполняйте Linux-захват.
Окно PowerShell с заданием должно оставаться открытым. Для анализа выбирается
валидный JSON-снимок, чей запрошенный интервал целиком находится внутри
Linux-захвата. Сам статус READY не подтверждает отказов или найденных связей;
он означает, что сохранён первый полный снимок с проверенной историей.
Буфер не создаёт службу или задание планировщика. Срок ограничен 600 секундами;
отдельный экспорт прерывается по тайм-ауту, ошибки сохраняются в статусе.

На машине с исходниками и Python-окружением проекта:

```sh
python -m rdp_guard.proxy_evidence \
  --windows rdp-proxy-windows.json --linux rdp-proxy-linux.jsonl
```

Файлы содержат сетевые адреса и имена машин. Реальные выгрузки следует хранить
отдельно от репозитория; в тестах используются синтетические данные.

## Условия дальнейшей приёмки

Полная цепочка наблюдалась в синхронном захвате ниже. Перед исполнением блокировок
нужны проверки намеренного повтора GUID, повторного использования порта,
перезапусков, потери записей, ротации журналов и дополнительного NAT перед Windows.
Конкретную версию Windows следует фиксировать отдельно: текущий экспорт её
не содержит, поэтому результат не доказывает совместимость всех версий ОС.
Снимок conntrack сам по себе не доказывает весь жизненный цикл соединения.
Диагностические JSON-файлы пока не аутентифицированы; их нельзя подключать к
исполнителю firewall.

## Как это станет подключением прокси в панели

Планируемая настройка содержит адрес прокси, исследуемый stream и связанный
Windows-хост. SSH используется для первоначальной установки и проверки узла;
root-пароль не должен становиться постоянным секретом веб-панели. Рабочий обмен
предполагает отдельную идентичность агента, взаимную аутентификацию и привязку
сертификата к конкретному серверу назначения и входному порту.

Linux-агент должен сам выводить IP из карты соединений. Команда от Windows вида
«заблокировать произвольный IP на всех портах» в протокол не входит. Для будущих
блокировок нужны срок действия, белый список, ограничения частоты, подтверждение
применения и отдельный журнал доказательств. Общий адрес ретранслятора нельзя
банить на Windows по совокупности ошибок проксируемых клиентов.

UI подключения, постоянный агент, защищённый обмен и исполнение правил в этом
прототипе ещё не реализованы.

## Проверка на действующем прокси

23 ноября 2026, 17:23:05–17:25:05 UTC, выполнен ограниченный диагностический
захват на OpenResty 1.27.1.2 в Docker. Временно включался INFO-журнал только
одного TCP stream; после захвата исходная конфигурация восстановлена байт в
байт, `nginx -t` и graceful reload прошли. Firewall и маршруты не менялись.

Сборщик сохранил 2016 записей без обнаруженных пропусков. Из 202 видимых
соединений 186 имеют полный жизненный цикл внутри захвата; у всех 186 найдено
единственное соответствие исходящего сокета по адресам и портам в conntrack.
Они относятся к 20 различным клиентским IP. При дополнительной проверке
поколений conntrack 5 соединений отклоняются: для одного peer tuple наблюдались
разные conntrack ID. Остаётся 181 однозначный кандидат по данным Linux.
Это подтверждает Linux-часть сопоставления, но пока не связывает эти соединения
с отказами аутентификации Windows.

Первая Windows-выгрузка за 17:23:30–17:23:40 UTC, выполненная в 17:27:36,
вернула 0 событий. Последующая диагностика показала круговой журнал размером
1 052 672 байта: в 17:30:10 он содержал 2077 записей только за
17:28:47–17:30:09 UTC — около 82 секунд истории. Запрошенный интервал к этому
моменту уже отсутствовал. Для повторной проверки нужны своевременно сохранённые
Windows-снимки; этот пустой экспорт не считается положительной проверкой.

Первый захват остановился раньше срока из-за слишком строгого сравнения
списков процессов. В исправленном сборщике обычное завершение старого worker
сохранено как изменение процесса, а повторное использование PID другой
идентичностью по-прежнему отклоняется. Неполный первый захват не исправлялся
задним числом. Реальные журналы хранятся отдельно от репозитория.

### Синхронный захват с сохранёнными Windows-событиями

Повторная проверка 23 ноября 2026: Linux 17:43:12–17:45:12 UTC,
Windows 17:43:37.558–17:44:07.558 UTC с дополнительными 5 секундами для событий
подключения. Временный Windows-буфер сохранил снимок до перезаписи журнала;
границы журнала до и после запроса подтвердили сохранность нужной истории.

- Windows: 101 событие, из них 56 событий 131 и 45 отказов 140.
- Для каждого отказа найдено ровно одно событие 131 с тем же ActivityID.
- Все 40 отказов, в которых Windows видит адрес исследуемого прокси,
  сопоставлены с 40 разными соединениями nginx и 12 исходными клиентскими IP.
- Остальные 5 отказов уже содержат другие IP источника в Windows. Они не
  сопоставились с этим stream; наличие другого видимого пути подключения
  не считается потерей сопоставления исследуемого прокси. Его устройство
  по этим данным не установлено.

Все значимые поля экспортированных событий дополнительно сверены с исходным
XML. На Linux захват не сообщил пропусков. После проверки исходная конфигурация
nginx восстановлена байт в байт, `nginx -t` прошёл; firewall и маршруты не менялись.
Реальные адреса, имена машин и сами журналы в репозиторий не добавлены.

Это положительный результат диагностического сопоставления в одном 30-секундном
окне Windows. Он не подтверждает защищённость ActivityID от намеренной подмены,
непрерывный учёт соединений при сбоях или готовность автоматических блокировок.
Прототип по-прежнему возвращает `enforcement_supported=false`.

## Основания

- [nginx: INFO-события связывают входящий и исходящий сокеты](https://trac.nginx.org/nginx/ticket/2440#comment:2).
- [Microsoft: ActivityID и RelatedActivityID](https://learn.microsoft.com/en-us/windows/win32/wes/eventschema-correlation-systempropertiestype-element).
- [Docker: опубликованные порты и MASQUERADE](https://docs.docker.com/engine/network/port-publishing/).

Общий смысл ActivityID документирован Microsoft. Связь конкретных событий
RdpCoreTS 131/140 проверяется на установленной версии Windows; она не объявляется
универсальной гарантией для всех реализаций RDP.
