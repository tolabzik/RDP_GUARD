# Контролируемая приёмка Windows Server 2022

Этот документ — инструкция будущего контролируемого теста, а не заявление о выполнении. На рабочем сервере ничего не устанавливать и не активировать без отдельного разрешения владельца.

1. Подготовить отдельную Windows Server 2022 VM, snapshot и независимый доступ к консоли. Зафиксировать исходные firewall-правила, RDP-порт, активные профили и audit policy.
2. Установить выпуск, создать администратора панели. Проверить LocalSystem для Guard Service, LocalService + service SID для Web Service, ACL ProgramData и бинарников, два запуска с задержкой и ограниченное восстановление после отказа.
3. В Monitor Only проверить доступ к панели только через 127.0.0.1:8787. С обычного RDS-пользователя запросить данные без логина, напрямую открыть pipe и SQLite: доступ к данным/управлению должен быть запрещён.
4. Добавить постоянный административный IP в whitelist. Убедиться в защите текущего WTS-администратора и предупреждении при неудачных попытках с его IP.
5. На отдельном внешнем тестовом IP, **не IP администратора**, выполнить меньше порога и затем 10 неудачных попыток за 5 минут. Проверить Event XML, источник, NTSTATUS, тип входа и отсутствие повторного подсчёта.
6. Для типа 3 подтвердить, что по умолчанию блокировки нет. Провести отдельный SMB-тест и не называть его доказанным RDP. 1149 должен оставаться контекстом.
7. Проверить остановку/запуск сборщика, bookmark, очистку журнала и видимое сообщение о разрыве. Сымитировать 1000 событий/минуту в течение 30 минут, измерить CPU/RAM и задержку принятия решения; целевые показатели — отсутствие потерь доступных событий и задержка до 5 секунд при штатной работе.
8. Только с доступной консолью пройти preflight ACTIVE. Проверить автоматический откат без подтверждения, включая падение Guard Service, недоступную панель и перезагрузку.
9. Повторно активировать и переподключиться с административного whitelist-адреса. Подтвердить подключение после нового 4624/10 или 4778. Проверить, что 1149/старое событие не позволяют подтверждение.
10. С тестового IP проверить фактическую TCP/UDP-блокировку только RDP-порта; убедиться в неизменности SQL, 1С, SMB, WinRM и исходящих соединений. Проверить все профили и IPv6-источник.
11. Проверить TTL, повторный бан, постоянный blacklist, ручное снятие/продление, whitelist перекрывающегося адреса, пустой список и предел ёмкости.
12. Остановить Guard Service и веб-службу, выполнить emergency-disable. Проверить удаление исключительно собственных правил и сохранение данных; исходные правила должны совпадать с baseline.
13. Проверить обновление, возврат старых бинарников при неудаче, сохранение базы/настроек, удаление с сохранением данных и отдельно `-PurgeData` на копии VM.
14. Повторить согласованные проверки на копии инфраструктуры с Kaspersky 14.2, SQL Server и 1С, затем отдельно разрешить production-установку в Monitor Only.

В протоколе указать версию/commit/SHA-256, ОС и patch level, тип RDP/NLA, адреса теста, Event XML без паролей, timestamps, реальные измерения нагрузки/задержки, исходные/итоговые правила, результаты SQL/1С/Kaspersky, проверку rollback и подпись ответственного администратора.
