# Восстановление после перезагрузки и сбоя

Начиная с **1.1.0-rc.4**, ежедневное выключение Windows не требует повторной
привязки `.rdpg` и ежедневного ручного включения ранее подтверждённой защиты.

## Один раз после обновления

1. Обновите Linux-пакет, затем Windows через `Update.ps1`. Сертификаты, привязка,
   списки и история сохраняются; повторный мастер Linux не нужен.
2. После `Update.ps1` Windows остаётся отключённым. В панели включите ACTIVE,
   переподключитесь по RDP и подтвердите подключение. Подтверждение сохраняет
   разрешение на последующее автоматическое восстановление.
3. На «Обзоре» должна появиться отметка «Автовосстановление разрешено».
   В «Прокси» сохранённый режим должен быть `enforce`, если нужны баны на Linux.
   Режим наблюдения автоматически не повышается до блокировок.
4. Проверьте один плановый перезапуск каждого типа сервера, сохранив резервный
   доступ. Дождитесь ACTIVE, свежего обмена прокси и фактических правил nftables.

## Ночью и утром

При выключении Windows свежие подтверждения перестают поступать. Linux не
продлевает правила по старому обмену: короткие разрешения nftables истекают.
Утром Windows самостоятельно запускает службы, запрашивает синхронизацию через
уже настроенный Windows Time и восстанавливает подписки на журналы.

Перед восстановлением ACTIVE проверяются firewall, RDP-порт и разрешающие
правила для доверенного адреса последнего подтверждения, доступность сторожевой
задачи, аудит, Security и корректность списка административных сессий. Входить
по RDP для этого не требуется. Пустой список сессий допустим; ошибка его чтения
оставляет защиту в ожидании. При неисправности повторная проверка идёт каждые
15 секунд, причина видна в панели.

Windows Time использует существующий источник, включая доменную политику.
После удачной синхронизации повтор — каждые 5 минут, при ошибке — каждые
30 секунд. Явно отключённая политикой служба времени не перенастраивается.

Linux при новой сессии сбора проверяет NTP и заново находит NPM по сохранённым
stream ID, входному порту, backend и каталогу данных. Новый PID namespace после
перезапуска контейнера принимается только при совпадении этой привязки. Пока
Docker/NPM/время недоступны, агент повторяет проверку через 5 секунд. Настройки
пользовательского RDP и stream не переписываются. Linux-службы должны оставаться
включёнными в автозапуске; явный `systemctl stop` не отменяется.

## Если служба остановилась

SCM запускает повторно упавшую службу с задержками 10, 60 и 300 секунд; последняя
попытка повторяется при дальнейших сбоях. Независимая задача SYSTEM дополнительно
проверяет службы каждую минуту и при загрузке, запускает остановленные Guard и
Web. При отсутствии рабочего heartbeat более 120 секунд она запрашивает
остановку Guard для восстановления. Насильно завершать зависший системный
процесс она не будет: если Windows не завершает STOP_PENDING, нужно проверить
SCM и защищённые журналы.

Команда `Stop-Service RDPGuardService` не является постоянным выключением
защиты: watchdog запустит службу снова. Для постоянного выключения используйте
**Monitor Only** или **Emergency Disable** в панели. Они отзывают разрешение
автовосстановления. Установщик/обновление/удаление выставляют ограниченную
30 минутами паузу, чтобы watchdog не мешал замене файлов.

Веб-панель запускается отдельно и при недоступности Guard показывает страницу
восстановления с последним числовым состоянием SCM. Когда Guard вернётся,
панель восстановит подключение либо предложит войти заново.

## Где смотреть причину

**Система → История службы и восстановления**: время запуска/остановки,
исключение, запрос повторного запуска, ожидание проверок, результат синхронизации
и события Windows SCM. Историю можно выгрузить в JSON. Локальный журнал хранит
последние 2000 записей в отдельной защищённой базе `service-events.sqlite3`.

Штатное завершение Windows отличается от команды STOP. Если процесс убит,
машина обесточена или ОС не сообщила инициатора, панель явно показывает, что
причина неизвестна; запись не приписывает остановку конкретному человеку.
Подробная история доступна после авторизации. Страница недоступности не
раскрывает адреса, пользователей, пути ключей и содержимое исключений.

Резервные источники: `%ProgramData%\RDPGuard\logs`, `web-logs` и системный журнал
Windows, источник **Service Control Manager**. На Linux —
`journalctl -u rdpguard-proxy.service` или соответствующий именованный экземпляр.

## Что меняется в списках прокси

Поиск по IP/части адреса, фильтр статуса, сортировка, страницы по 50 адресов,
копирование IP, экспорт страницы, выбор нескольких адресов и снятие их банов.
Снятие направляется на конкретный stream и подавляет повторные решения на время
окна обнаружения; оно не добавляет адрес в белый список. Доверенные сети Linux
показаны отдельно от белого списка Windows и здесь доступны только для чтения.

Для поиска по всей базе нужен Linux rc.4. Со старым агентом отображается последняя
полученная выборка с сообщением об ограничении. Протокол передачи событий и
существующие сертификаты совместимы с rc.3.
