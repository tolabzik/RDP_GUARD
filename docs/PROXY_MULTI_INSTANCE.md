# Несколько Windows-узлов на одном Linux/NPM

**Разработка в `codex/proxy-multi-instance`, ещё не опубликованный релиз.**
Команды ниже требуют пакета из этой ветки. Опубликованный установщик `1.1.0-rc.2`
пока их не содержит. Номер выпуска и установщик обновляются при подготовке релиза;
CI-артефакты ветки предназначены для проверки на стенде, а не обновления production.

## Что устанавливается

Пакет `rdpguard-proxy` ставится на Linux один раз. Каждый защищаемый stream получает
свою службу systemd, HTTPS-порт, ключи, базу, настройки и таблицу nftables.
Отдельный процесс диспетчера не нужен: запуск и перезапуск выполняет systemd.
Остановка одного узла не останавливает остальные.

Пример (второй stream и его порты условные):

| Узел | Вход RDP | HTTPS API | Служба |
|---|---|---|---|
| Уже настроенный | `45.144.220.53:45451` | `:9443` | `rdpguard-proxy.service` |
| Бухгалтерия | `45.144.220.53:45452` | `:9444` | `rdpguard-proxy@accounting.service` |

Прежний экземпляр называется `default`. Его файлы и имя службы остаются прежними.
Разрешение блокировок, сертификаты и сохранённые настройки при добавлении второго
узла не сбрасываются. У нового узла свои адреса администраторов и отдельная привязка
Windows; принятие одного узла не разрешает автоматически блокировки на другом.

Бан на первом stream действует только на его входной IP/порт. Клиент с тем же IP
остаётся доступен на втором stream, пока тот независимо не заблокирует его.

## Как добавить второй узел

1. В NPM создайте обычный TCP stream на другой Windows-сервер и проверьте RDP.
2. На этом Windows установите RDP Guard с поддержкой `.rdpg`, откройте «Прокси».
   Протокол обмена не изменён; Windows `1.1.0-rc.2` поддерживает эту привязку.
3. На Linux выполните:

   ```sh
   sudo rdpguard-proxy add --instance accounting
   ```

   Без `--instance` мастер спросит имя. Доступны строчные латинские буквы, цифры
   и дефис, первая буква обязательна, длина до 32 символов. `default` зарезервировано.
4. Выберите свободный stream. Мастер предложит следующий не занятый конфигурациями
   HTTPS-порт, обычно `9444`. Если его занимает другая программа, настройка завершится
   до применения изменений; повторите с другим портом. Обеспечьте доступ именно этого
   Windows к новому HTTPS-порту — мастер не меняет сетевой firewall.
5. Подтвердите показанный план. Передайте созданный `/root/rdpguard-accounting.rdpg`
   второму Windows и импортируйте через «Прокси → Подключить файлом».
   Оставьте SSH-окно открытым до завершения; окно приглашения — 10 минут.
6. Проверьте связь и сопоставление IP в Windows. Новый экземпляр начинает в наблюдении.
   Для блокировок требуется отдельная проверка его пути трафика и включение защиты.

Повторная установка `.deb` или копирование ключей первого Windows не требуется.
Одновременный запуск двух мастеров запрещён. Повторный `setup` при существующих
узлах предлагает добавить именованный экземпляр.

## Просмотр и обслуживание

```sh
sudo rdpguard-proxy list
sudo rdpguard-proxy doctor
sudo rdpguard-proxy doctor --instance accounting
sudo rdpguard-proxy status --instance default
sudo journalctl -u rdpguard-proxy@accounting.service -n 40 --no-pager
sudo systemctl restart rdpguard-proxy@accounting.service
```

`list` показывает имена, Windows-компьютеры, входные адреса и HTTPS-порты без секретов.
`doctor` без имени проверяет все сохранённые привязки. `status` без имени показывает
все их службы. Фактический режим защиты смотрите в соответствующей Windows-панели:
разрешение enforcement в конфигурации само по себе не подтверждает действующие баны.

Новые файлы находятся в:

- `/etc/rdpguard-proxy/instances/accounting/` — конфигурация и сертификаты;
- `/var/lib/rdpguard-proxy/instances/accounting/` — SQLite, состояние мастера и backup.

## Общий журнал, обновление и отключение

У каждого NPM-контейнера остаётся один INFO include и один журнал. Второй узел
использует уже включённый журнал без дополнительного reload nginx. Все агенты
читают его независимо и сопоставляют только свой backend. Ротация общая: один
таймер обрабатывает каждый уникальный журнал один раз. Привязка нового Windows
не приостанавливает ротацию ранее работающих узлов.
После сохранения привязки общий таймер включён в автозапуск независимо от автозапуска
самих агентов: NPM продолжает писать журнал даже при остановленных агентах.

При обновлении пакета ранее работавшие экземпляры останавливаются и запускаются
вновь. Остановленные экземпляры не запускаются, состояние автозапуска сохраняется.
Ключи и базы сохраняются. Завершите мастер привязки перед обновлением пакета.

Чтобы отключить только второй узел:

```sh
sudo rdpguard-proxy unconfigure --instance accounting
```

Команда показывает план и просит подтверждение. Она останавливает и отключает
автозапуск выбранной службы. Если журнал нужен другим узлам, include и ротация
остаются. Исходный include восстанавливается только после отключения последнего
пользователя этого журнала. Изменённый вручную include автоматически не перезаписывается.

Ключи, конфигурация, база и исходные backups сохраняются даже после `unconfigure`.
Не удаляйте эти каталоги вручную: backup первого узла может быть нужен остальным.
Имена и сетевые привязки сохранённых конфигураций остаются зарезервированными;
повторное использование требует отдельной миграции. Автоматической перепривязки
или уничтожения сохранённых данных эта доработка не добавляет.

Для удаления всего пакета сначала выполните `unconfigure --instance …` для всех
узлов из `list`, включая `default`, если он есть. При нескольких узлах команда
без имени откажется выбирать за оператора. Затем можно выполнить `apt remove`.

## Ограничения

- До 32 настроенных узлов. Это защитный предел, не заявленная производительность:
  нагрузка сборщиков растёт с количеством экземпляров, каждый читает общий журнал
  и принимает события conntrack. Массовое размещение требует нагрузочного теста.
- Одна привязка — один IPv4 TCP stream и один backend `IP:port`.
  Дубли входного IP/порта, backend и идентификатора stream отклоняются.
- У каждого Windows отдельный HTTPS-порт. Единого сетевого API-диспетчера нет.
- UDP и IPv6 автоматически не защищаются. NAT, меняющий peer IP/порт после Linux,
  и автоматическое восстановление привязки при пересоздании NPM не добавлены.
- Успешный `doctor` не заменяет сквозную проверку нового Windows и его маршрута.
