# Установка Linux-агента и подключение Windows

Начиная с `1.1.0-rc.3`, один Linux-пакет обслуживает несколько Windows через
отдельные экземпляры служб. [Добавление второго узла](PROXY_MULTI_INSTANCE.md).

Выпуск **1.1.0-rc.3**, пакет для **Ubuntu 24.04 amd64** с уже работающим
Nginx Proxy Manager в Docker. Пакет содержит приложение и его Python-библиотеки;
`apt` устанавливает системные зависимости. Вручную создавать venv или запускать
pip на сервере не требуется. Начальный режим интеграции — наблюдение;
новые привязки получают `enforcement_validated=false` до проверки их схемы.
Обновление сохраняет уже установленное разрешение блокировок для существующих узлов.

## 1. Подготовить Windows

Скачайте [Windows ZIP](https://github.com/tolabzik/RDP_GUARD/releases/download/v1.1.0-rc.3/RDPGuard-1.1.0-rc.3-win-x64.zip)
и [его SHA256](https://github.com/tolabzik/RDP_GUARD/releases/download/v1.1.0-rc.3/RDPGuard-1.1.0-rc.3-win-x64.zip.sha256).
Проверьте хеш командой `Get-FileHash` и распакуйте ZIP полностью.
Из распакованной папки в PowerShell администратора:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File ".\Update.ps1"
```

Для первой установки замените `Update.ps1` на `Install.ps1`. Установщик запросит
имя и пароль администратора панели через `rdpguard.exe init-admin`; отдельный
запуск этой команды после успешной установки не нужен. При обновлении учётная
запись, настройки, списки и история сохраняются, создаётся резервная копия;
локальная защита Windows остаётся в Monitor Only.

Откройте **http://127.0.0.1:8787 → Прокси**. Подготовьте Windows до запуска мастера
Linux: срок приглашения `.rdpg` ограничен десятью минутами. Для наблюдения прокси
включение Windows ACTIVE не требуется. Новая сборка проверяется на Server 2022;
Server 2012 R2 пока не подтверждён.

## 2. Одна команда на Linux

В интерактивной SSH-консоли Linux выполните следующую строку. Нужен установленный
`curl`, доступ к GitHub и репозиториям Ubuntu, root либо права `sudo`:

```bash
(set -e; rdp_installer=$(mktemp); trap 'rm -f "$rdp_installer"' EXIT; curl -fL --proto '=https' --tlsv1.2 'https://github.com/tolabzik/RDP_GUARD/releases/download/v1.1.0-rc.3/Install-ProxyRelease.sh' -o "$rdp_installer"; bash "$rdp_installer")
```

Установщик конкретного релиза скачивает `.deb` и `.sha256`, сверяет SHA256,
имя, версию и архитектуру пакета, затем устанавливает его и запускает мастер.
Он сохраняет интерактивный ввод: не запускайте установщик через `curl | bash`.
При существующей конфигурации выполняется обновление без повторной привязки.

Для ручной установки скачайте [.deb](https://github.com/tolabzik/RDP_GUARD/releases/download/v1.1.0-rc.3/rdpguard-proxy_1.1.0-rc.3_amd64.deb)
и [SHA256](https://github.com/tolabzik/RDP_GUARD/releases/download/v1.1.0-rc.3/rdpguard-proxy_1.1.0-rc.3_amd64.deb.sha256)
в один каталог, затем:

```sh
sha256sum -c rdpguard-proxy_1.1.0-rc.3_amd64.deb.sha256 && \
  sudo apt install ./rdpguard-proxy_1.1.0-rc.3_amd64.deb && \
  sudo rdpguard-proxy setup
```

Переходите к установке только при результате `OK` проверки SHA256. Имя файла
содержит `1.1.0-rc.3`; внутри Debian-пакета версия записана как `1.1.0~rc3`
для правильного порядка обновлений в `apt`.

## 3. Пройти мастер и импортировать файл

Выберите TCP stream NPM и укажите реальные внешние IP администраторов.
Windows должен иметь доступ к HTTPS-порту агента на Linux, по умолчанию `9443`;
мастер сам не открывает firewall. Сохраняется прежний внешний RDP-адрес пользователей.

После создания `.rdpg` оставьте мастер открытым. Передайте файл на нужный Windows
и в течение 10 минут выберите **Прокси → Подключить файлом**, проверьте адрес
ретранслятора и подтвердите доверие. Пароль root и ручная передача закрытых ключей
не нужны. Дождитесь завершения мастера и свежих статусов в панели: связь, события
и сопоставление IP проверяются отдельно.

## Что меняет установка

Установка пакета не включает защиту, не запускает агент и не меняет nginx,
маршруты или firewall. Мастер предназначен для новой установки с уже работающим
Nginx Proxy Manager в Docker. Ручную установку в `/opt/rdpguard-proxy` нужно
мигрировать отдельно: пакет отказывается перезаписывать её.

Мастер сначала читает контейнеры и stream-конфигурации. Затем предлагает выбрать
stream, конкретный IP входа и реальные адреса администраторов, показывает все
изменения и просит одно подтверждение. Каждый экземпляр обслуживает один IPv4 TCP stream с
конкретным IPv4 backend; TLS-терминация, изменённый внешний порт Docker,
неизвестные include и несколько replicas не принимаются. UDP и IPv6 остаются
вне выбранной области защиты.

После подтверждения мастер добавляет отдельный INFO-журнал через поддерживаемый
custom include NPM, сохраняя исходный файл и проверяя `nginx -t`. Генерируемые
stream-файлы не редактируются. Include действует на все TCP streams. Пакет
включает отдельную ротацию этого INFO-журнала: проверка раз в 5 минут, порог
16 MiB, 7 архивов. Между проверками файл может превысить порог. После переименования
файла выполняется `nginx -s reopen` в выбранном контейнере. Ротация создаёт разрыв
наблюдения: агент закрывает старую эпоху и собирает новую, не продолжая её молча.
При неудаче мастер возвращает исходный include только если его не менял кто-то
ещё; чужие параллельные изменения не перезаписываются.

Создаётся один временный файл `.rdpg`. Передайте его на нужный Windows-сервер
защищённым способом и импортируйте через новую панель RDP Guard. Файл содержит
одноразовый секрет: не публикуйте его. Окно привязки работает до 10 минут. Linux
ждёт отдельное подтверждение, что Windows сохранил сертификат и привязку.
После этого временный endpoint закрывается, приватный ключ CA удаляется с Linux;
постоянный обмен использует клиентский сертификат. Агент запускается в monitor,
автозапуск выбирается отдельно в мастере. IP прокси исключается из локальных
блокировок Windows при сохранении привязки.

Если сертификат уже выдан, но подтверждение Windows не пришло до истечения
10 минут, мастер сообщает о незавершённой настройке и возвращает ошибку. Linux
сохраняет установленную привязку и запускает monitor для клиента, успевшего
сохранить сертификат; автозапуск не включается. Проверьте состояние в Windows.
При потере сертификата нужна новая привязка с новыми ключами, а не повторное
использование истёкшего файла. Исходный `.rdpg` удаляется на Linux при завершении
мастера; переданную копию также следует удалить после импорта.

Для наблюдения Windows ACTIVE не требуется. Адреса администраторов в Linux
whitelist независимы от Windows whitelist. У новой привязки Linux gate равен
`enforcement_validated=false`: сама привязка не включает блокировки.

`rdpguard-proxy status` показывает состояние службы; `rdpguard-proxy doctor`
проверяет конфигурацию и доступность локальных компонентов без изменений.
PID namespace закреплён за выбранным контейнером. Перезапуск/пересоздание NPM
может сменить его: агент в этом случае прекращает доверять наблюдению, а
`doctor` показывает несовпадение. Автоматической перепривязки в этой версии нет;
нужны сверка контейнера/scope, обновление namespace в конфигурации и перезапуск
агента. Ротация тоже закреплена за полным ID контейнера; при его замене нужно
проверить и обновить её цель. До восстановления наблюдения блокировки недоступны.

При обновлении пакета конфигурация, ключи и SQLite сохраняются. Ранее работавшие службы
останавливаются на время замены и запускаются вновь; остановленные экземпляры не
запускаются, состояние автозапуска сохраняется. Для прежнего узла перед удалением выполните:

```sh
sudo rdpguard-proxy unconfigure --instance default
sudo apt remove rdpguard-proxy
```

Если узлов несколько, сначала отключите каждый через `unconfigure --instance ИМЯ`
(имена показывает `rdpguard-proxy list`). Общий include и ротация сохраняются, пока
они нужны другим узлам. Последний узел восстанавливает исходный INFO include,
если его байты не менялись после установки, и отключает ротацию.
Если include редактировали вручную, восстановление останавливается; backup и
его путь сохраняются в `/var/lib/rdpguard-proxy/setup-state.json`. Нужно вручную
сверить исходный файл с текущим, убрать managed INFO block, выполнить `nginx -t`
и reload; не копируйте backup поверх новых настроек без проверки. Пакет
отказывается удаляться, пока его marker указывает на активный INFO include,
чтобы не оставить растущий журнал без ротации. Вручную исправленную конфигурацию
должен проверить оператор перед изменением marker `logging_active` на `false`.

`apt remove` останавливает и отключает unit, но сохраняет пользовательские данные.
Даже `apt purge` не удаляет
ключи, SQLite и nginx-журналы автоматически.

Дополнительный NAT между backend и Windows, меняющий peer IP/порт, сейчас не
поддерживается. До production enforcement нужны проверки реального NPM/Docker,
Windows-событий, NAT и сохранения доступа легитимных пользователей; изолированный
Linux DNAT/nftables harness эту сквозную проверку не заменяет.
