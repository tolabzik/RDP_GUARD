# Агент для nginx stream: установка и приёмка

Начиная с **1.1.0-rc.2**, агент входит в выпуск RDP Guard из `main`.
Для Ubuntu 24.04 amd64 используйте [установку одним пакетом и файлом привязки](PROXY_SETUP.md).
Ниже описаны устройство, ограничения и альтернативная ручная установка из wheel;
ручные шаги не нужно повторять после мастера `.deb`.
Новый узел начинает с `enforcement_validated=false` до проверки его схемы.
Обновление сохраняет уже разрешённые блокировки существующих узлов. Адрес RDP
и обычный клиент mstsc сохраняются, RD Gateway не требуется.
С **1.1.0-rc.3** доступны [несколько экземпляров на одном Linux](PROXY_MULTI_INSTANCE.md).

Windows передаёт исходные события RdpCoreTS 131/140 по HTTPS с взаимной проверкой
сертификатов. Linux сопоставляет ActivityID, исходящий сокет nginx, записи NAT и
исходный клиентский IP. API привязан к одному сертификату, stream и Windows-хосту.
Решение без однозначной цепочки не получает разрешение на блокировку. Общий IP
прокси исключается из локальных блокировок Windows после настройки привязки.

## Что подготовить для ручной установки

- Linux-хост nginx с root-доступом, Python **3.12+**, systemd и conntrack netlink.
  Сборщик работает на хосте, чтобы видеть Docker NAT и пространства PID.
  Для отдельного этапа исполнения нужны nftables и поддержка timed sets ядром.
- Собранный из тега нужного выпуска wheel `rdp_guard-*.whl` и каталог совместимых Linux
  wheels всех зависимостей. Установщик использует `pip --no-index`, сетевых
  загрузок не выполняет. Wheel для Windows и его зависимости не подходят Linux.
- Windows-пакет **1.1.0-rc.2** с командами `proxy-configure` и `proxy-status`.
  Старые выпуски 1.0.0-rc.* не содержат интеграции прокси.
- Точное значение `Computer` из XML событий защищаемого Windows-сервера,
  реальные внешние IP администраторов, адрес назначения stream и путь к INFO-логу.
- Отдельный достижимый Windows→Linux адрес API. Порт API не является портом RDP.
  Доступ к API следует ограничить нужным Windows-узлом на существующем сетевом
  периметре; этот установщик не меняет firewall или маршруты.

Дополнительный NAT между выбранным backend и Windows должен сохранять peer IP
и исходящий порт Linux. Сборщик сейчас читает conntrack только данного Linux-хоста:
получение сопоставлений с другого маршрутизатора ещё не реализовано. Если он меняет
peer IP или порт, такая схема пока не поддерживается. Один IP прокси в Windows
ещё не доказывает сохранность порта на промежуточном маршрутизаторе.

## Однократная подготовка сертификатов

На доверенной машине с Python и OpenSSL выполните пример, заменив **все** адреса,
имя Windows и путь журнала на фактические. Адреса ниже документационные.
Каталог результата должен быть новым; существующие файлы не перезаписываются.
[Образец config.json](../deploy/proxy-agent.example.json) показывает поля, но его
нулевой fingerprint не рабочий: используйте конфигурацию, созданную bootstrap.

```sh
python3 scripts/Bootstrap-Proxy.py \
  --output /secure/new-rdp-proxy-bundle \
  --agent-host 192.0.2.10 --api-bind-ip 192.0.2.10 --api-port 9443 \
  --computer WIN-SERVER.example.test --stream-id rdp-45451 --backend-id windows-1 \
  --backend-ip 192.0.2.20 --backend-port 45451 \
  --listener-ip 192.0.2.10 --listener-port 45451 \
  --relay-ip 192.0.2.10 --admin-network 198.51.100.7/32 \
  --nginx-log /srv/npm/data/logs/rdpguard-stream-info.log \
  --nginx-utc-offset-minutes 0
```

`--agent-host` становится SAN сертификата и адресом HTTPS в Windows. При DNS-имени
его разрешение на Windows должно вести к указанному Linux API. `--api-bind-ip`
задаётся отдельно; без него API слушает только `127.0.0.1`. `--relay-ip` — адрес,
который видит Windows в событии 131; допускается несколько таких аргументов.
`--listener-ip` — конкретный публичный IP назначения RDP, который ограничивает
область firewall. Значения `0.0.0.0`/`::` здесь запрещены; wildcard в самом INFO-логе
nginx распознаётся отдельно. `--admin-network` можно повторять для реальных адресов и подсетей администраторов.

Результат:

| Каталог | Куда передавать | Содержимое |
| --- | --- | --- |
| `linux/` | Только Linux-агенту | config.json, ca.pem, server.pem, server.key |
| `windows/` | Только привязанному Windows | binding.json, ca.pem, client.pem, client.key |
| `ca/` | Хранить отдельно, не устанавливать | CA и закрытый ключ выпуска сертификатов |

На POSIX-системах каталоги создаются с правами `0700`, файлы — `0600`. Если bootstrap
запускается на Windows, заранее ограничьте NTFS ACL родительского каталога своим
администратором и SYSTEM: chmod не устанавливает Windows ACL. Windows-копии также
требуют ACL, указанных ниже. Пароль SSH не запрашивается и нигде не сохраняется.
Сертификаты клиента/сервера действуют 365 дней; CA — 3650 дней. Заранее
запланируйте обновление сертификатов и fingerprint привязки. Просроченный
сертификат останавливает защищённый обмен. Автоматического продления пока нет.

Bootstrap всегда создаёт `enforcement_validated: false` и Windows `mode: monitor`.
Подпись и совпадение ключей проверяются локально; это не проверка работы RDP/NAT.

## INFO-журнал в Nginx Proxy Manager

NPM поддерживает файл `/data/nginx/custom/server_stream_tcp.conf`, включаемый
**во все TCP stream server-блоки**. Это глобальная область TCP streams, а не
настройка только одного порта. [Документация NPM](https://nginxproxymanager.com/advanced-config/#custom-nginx-configurations).

Содержимое примера [nginx-stream-info.conf.example](../deploy/nginx-stream-info.conf.example):

```nginx
error_log /data/logs/rdpguard-stream-info.log info;
```

Сохраните исходный custom include и вручную объедините строку с существующим
содержимым. Не заменяйте весь include примером и не редактируйте генерируемые
`/data/nginx/stream/*.conf`: NPM пересоздаёт их. После проверки итоговой конфигурации
командой `nginx -t` выполняется отдельный graceful reload. Ручной `Install-ProxyAgent.sh` эти действия
не выполняет. Мастер `.deb` управляет include и ротацией по [отдельной процедуре](PROXY_SETUP.md).

Сопоставьте `/data/logs/...` внутри контейнера с реальным путём на Linux-хосте;
именно host-путь нужен `nginx_log`. Часовой пояс nginx может отличаться от хоста.
При нескольких nginx PID namespaces укажите фактический `nginx_pid_namespace`
из `/proc/<host-pid-nginx>/ns/pid`; автоматический выбор работает только при одном.

INFO-записи появляются от **всех** TCP streams. Сопоставление ограничено выбранным
listener/backend, но сборщик читает общий файл, поэтому остальные streams тоже
увеличивают объём и расходуют лимит. Оцените скорость роста файла и обеспечьте
ротацию/retention на стороне эксплуатации. Агент сам не удаляет журналы.
При смене inode, обрезании файла, переполнении netlink, разрыве PID-истории или
лимите памяти текущая эпоха становится недоступной; новый сбор начинается с EOF.
Обычная смена workers после graceful reload допускается. Фиксированный namespace
после пересоздания контейнера нужно сверить и при необходимости обновить.

Одна эпоха длится до 900 секунд, содержит до 100000 записей и читает до 64 MiB
нового лога. Снимок публикуется только после завершения conntrack dump и фактического
освобождения очередей/дочитывания файла. Старше 10 секунд он считается устаревшим.
Переход к новой эпохе создаёт окно недоступности: неполные связи не переносятся.
Долгое соединение, начатое до эпохи, не становится подтверждённым по одному снимку.
Отсутствие замеченных потерь не является гарантией полноты транспортных журналов.

## Установка на Linux

Передайте wheel, Linux wheelhouse, каталог `linux/`, скрипт установки и папку
`deploy/` на Linux обычным защищённым способом. Из checkout тега выбранного выпуска:

```sh
sudo bash scripts/Install-ProxyAgent.sh \
  /secure/rdp_guard-VERSION-py3-none-any.whl \
  /secure/new-rdp-proxy-bundle/linux /secure/linux-wheelhouse
```

Установщик принимает только новую установку, создаёт закрытые конфигурацию и
состояние, проверяет конфигурацию и регистрирует unit. Он **не запускает** и
**не включает автозапуск** службы, не меняет nginx, Docker, firewall или маршруты.
Существующие каталоги установки он не перезаписывает. При незавершённой установке
сначала разберите ошибку; автоматического обновления поверх частичного результата нет.

После проверки конфигурации и пути к журналу:

```sh
sudo /opt/rdpguard-proxy/venv/bin/rdpguard-proxy \
  --config /etc/rdpguard-proxy/config.json --check-config
sudo systemctl start rdpguard-proxy
sudo journalctl -u rdpguard-proxy -n 60 --no-pager
```

Начальный режим остаётся наблюдением. Автозапуск включается отдельно после приёмки:
`sudo systemctl enable rdpguard-proxy`. Unit запускается от root для чтения host
conntrack и пространства процессов; файлы ключей и SQLite доступны только root.
Конфигурация находится в `/etc/rdpguard-proxy`, состояние — `/var/lib/rdpguard-proxy`.

## Подключение Windows

Создайте новый защищённый каталог и скопируйте туда **только** Windows-bundle.
Из PowerShell администратора; замените путь к переданному bundle:

```powershell
$proxyRoot = Join-Path $env:ProgramData 'RDPGuard\proxy'
if (Test-Path $proxyRoot) { throw 'Каталог уже существует: сначала проверьте текущую привязку.' }
New-Item -ItemType Directory -Path $proxyRoot | Out-Null
$proxyAcl = New-Object System.Security.AccessControl.DirectorySecurity
$proxyAcl.SetAccessRuleProtection($true, $false)
foreach ($proxySid in @('S-1-5-18', 'S-1-5-32-544')) {
    $proxyIdentity = New-Object System.Security.Principal.SecurityIdentifier($proxySid)
    $proxyRule = New-Object System.Security.AccessControl.FileSystemAccessRule(
        $proxyIdentity, 'FullControl', 'ContainerInherit,ObjectInherit', 'None', 'Allow')
    $proxyAcl.AddAccessRule($proxyRule)
}
Set-Acl -Path $proxyRoot -AclObject $proxyAcl
Copy-Item 'C:\Secure\new-rdp-proxy-bundle\windows\*' -Destination $proxyRoot
$proxyGuard = Join-Path $env:ProgramFiles 'RDPGuard\rdpguard.exe'
& $proxyGuard proxy-configure --file (Join-Path $proxyRoot 'binding.json')
& $proxyGuard proxy-status
```

Пример предполагает стандартный `C:\ProgramData`; при другом DATA_DIR исправьте
три пути в binding.json до импорта. Ключи должны находиться внутри `DATA_DIR\proxy`;
ссылки и выход за этот каталог отклоняются. Панель позволяет настроить такую же
привязку в разделе прокси. Обновлять действующий ключ нужно отдельной процедурой,
с проверкой fingerprint на Linux; копирование нового ключа само по себе недостаточно.

## Приёмка перед блокировками

Сначала подтвердите работу наблюдения на контролируемых соединениях: один клиент
с намеренной ошибкой пароля и другой с успешным входом. Нужны отдельные реальные
адреса, не общий адрес прокси. Проверьте цепочку обоих подключений и однозначность
NAT-портов, включая параллельные попытки. Администратор должен быть в whitelist
**на Linux по исходному адресу**, а адрес ретранслятора — в Windows binding.

Дополнительно обязательны проверки ротации INFO-лога, потерь/перезапуска агента,
перезапуска NPM, пропуска Windows-журнала, повторного использования PID/порта,
ошибочного сертификата, недоступности API и восстановления. Для реальных правил
нужно отдельно проверить область listener/протокола, срок бана, снятие правила,
сохранение доступа легитимного клиента и резервную консоль. Синтетические pytest
не заменяют эти проверки на целевых ОС.

До успешной приёмки оставьте `enforcement_validated: false` на Linux и `monitor`
на Windows. Разрешение блокировок требует обеих сторон и отдельного подтверждения
в панели; обходить этот этап правкой случайного флага не следует. Настройка
`protocols` по умолчанию содержит только `tcp`; наличие UDP-stream в NPM ещё не
подтверждает, что выбранный исполнитель проверен для UDP.

Остановить агент: `sudo systemctl stop rdpguard-proxy`. При штатном завершении
агент пытается снять собственные блокировки. Записи ядра имеют короткую аренду
не более 30 секунд и перестают продлеваться при потере агента/валидных данных.
Эта логика проверена переносимыми тестами; реальное истечение на целевом ядре
Linux ещё входит в приёмку. При включённом только наблюдении правил нет.

## Обновление и возврат ручной установки из wheel

`Install-ProxyAgent.sh` предназначен только для первой установки. Повторный
bootstrap не является обновлением: он меняет доверенный CA и fingerprint.
Существующие config.json, сертификаты и SQLite при обновлении сохраняются.
Для ручной установки из wheel автоматического updater нет. Обновление `.deb`
с сохранением конфигурации описано в [руководстве пакета](PROXY_SETUP.md).

Порядок отдельного согласованного обновления:

1. Подготовьте новый локальный wheel и Linux wheelhouse, зафиксируйте SHA256 и
   сохраните предыдущий wheel с зависимостями. Проверьте release notes на
   совместимость схемы SQLite и протокола с установленной Windows-сборкой.
2. Переведите Windows-привязку в `monitor`. Зафиксируйте, работала ли служба и
   был ли включён автозапуск. Остановите `rdpguard-proxy`; убедитесь, что процесс
   завершён. Не копируйте открытый SQLite-файл обычным `cp`.
3. Создайте новый root-only каталог резервной копии (0700). Сохраните туда
   `/etc/rdpguard-proxy`, `/var/lib/rdpguard-proxy` целиком, включая возможные
   `-wal`/`-shm`, текущий systemd unit и сведения о версии. Файлы копии — 0600.
   Конфигурация, сертификаты и база образуют один согласованный комплект той же
   привязки. Пока идёт копирование, служба остаётся остановленной.
4. Пока служба остановлена, создайте новое Python 3.12 окружение в отдельном
   постоянном каталоге версии, установите wheel с `--no-index --find-links` и
   проверьте его командой `rdpguard-proxy --config ... --check-config`.
   Запустите проверки новой версии до смены рабочего ExecStart. Окружение venv
   после установки не перемещайте: его исполняемые скрипты содержат абсолютные пути.
5. Замените только ExecStart через отдельный systemd drop-in на проверенный
   постоянный путь версии, сохранив исходный drop-in или его отсутствие.
   Выполните `systemctl daemon-reload`. Запуск — отдельным явным действием;
   ранее остановленная служба не должна запускаться автоматически. Автозапуск
   сохраните в прежнем состоянии.
6. После запуска проверьте TLS, native coverage, checkpoint и контролируемые
   соединения. При ошибке остановите службу, верните предыдущий ExecStart и
   конфигурацию. При несовместимом изменении базы восстановите **остановленную**
   SQLite из полного комплекта резервной копии; не смешивайте старый основной
   файл с новыми WAL/SHM. Предыдущая версия запускается только явно, в monitor.

Этот порядок требует проверки на целевом Linux до автоматизации. Откат wheel
без проверки совместимости базы не считается безопасным откатом.

## Смена сертификата клиента или привязки

SQLite закреплён за fingerprint **клиентского** сертификата, stream/backend,
Windows-хостом, обоими сетевыми endpoints, relay IP и протоколами. Изменение
любого из этих полей с прежней базой намеренно отклоняется. Перевыпуск только
серверного сертификата с прежним доверенным CA не меняет fingerprint клиента.

Для смены клиентского сертификата сначала переведите обмен в monitor, подтвердите
снятие правил старой привязки, остановите службу и сохраните согласованный комплект
конфигурации, ключей и базы по процедуре выше. Подготовьте новый клиентский ключ и
сертификат, соответствующий `client_sha256` на Linux и Windows-bundle. Укажите в
Linux-конфигурации **новый, ещё не существующий** файл внутри защищённого каталога,
например `/var/lib/rdpguard-proxy/state-cert-YYYYMMDD.sqlite3`; одноимённых WAL/SHM
также быть не должно. Старую базу сохраните вместе со старой привязкой.

Не редактируйте запись identity внутри SQLite и не переносите решения/баны между
привязками вручную. Новая база начинает без прежних решений, в monitor, с повторной
проверкой TLS и цепочки событий. При откате возвращается целиком старый комплект
«конфигурация + сертификаты + база», пока служба остановлена. После этого запуск
снова выполняется явно; автоматического переноса доверия между ключами нет.
