# Отчёт о проверках

## Локальная проверка

В разработке выполнены автоматизированные unit/integration-тесты ядра, SQLite, API и безопасности панели на macOS / Python 3.13: **131 passed**. Ruff и синтаксис обоих браузерных JavaScript-файлов проверены. Одиннадцать нативных Windows-проверок на macOS пропускаются.

Дополнительно проверены вход, dashboard, форма настроек, тёмная и светлая темы в браузере при узком и настольном viewport. Снимок находится в `docs/images/dashboard.jpg`, данные искусственные. Синтетическая локальная запись 1000 событий типа 3 в SQLite WAL с транзакционными bookmarks заняла около 0,18 секунды (5622 события/с); это измерение ядра на машине разработки, не доказательство end-to-end производительности Windows-сборщика.

Проверяются: порог, окно, дедупликация, повторно используемые Record ID, atomic bookmark, парсинг/NTSTATUS, тип 3 vs 10, whitelist и активные администраторы, недостоверная WTS-информация, TTL/эскалация, IPv4/mapped/IPv6, Monitor Only, circuit breaker, ошибки/read-back firewall, ownership, пустые списки, запрет wildcard, активация/откат/подтверждение, atomic import, безопасные параметры, Argon2id, CSRF, loopback, Origin/Host, session expiry/logout, login throttling, подмена RPC-идентичности и экспорт без секретов.

## Проверки GitHub Actions

Workflow `.github/workflows/ci.yml` запускает тесты на Python 3.12 / Linux и Windows Server 2022. Windows-тесты создают и проверяют узкие TCP/UDP firewall-правила с IPv4/IPv6 документационными адресами, затем снимают их и сравнивают исходный набор. Подписка и bookmark проверяются настоящим Windows Event Log API.

После PyInstaller сборки выполняется настоящая установка frozen-служб, login через LocalService → named pipe → SYSTEM, защищённая команда whitelist, проверка loopback listener, запрет ACTIVE при непрошедшем preflight, отказ обычному Windows-пользователю в доступе к pipe/SQLite, независимый watchdog с реальным удалением своих правил и emergency-команда после остановки служб. Отдельный нативный тест проверяет Windows-идентичность клиента и обмен сообщениями Named Pipe. JUnit и журналы служб сохраняются в artifacts. Release публикуется только после успеха всех обязательных jobs.

Точный итог каждого прогона и commit доступны в [Actions](https://github.com/tolabzik/RDP_GUARD/actions). Если workflow не прошёл, выпуск не считается собранным/проверенным.

Для rc.2 добавлены: подключение клиента до `ConnectNamedPipe` в отдельном процессе с таймаутом; 200 запросов при двух и восьми одновременных клиентах с проверкой отсутствия потерь и повторного исполнения; 100 параллельных `status/events` через HTTP установленной панели и проверка CLI после нагрузки. Переносимые тесты проверяют гонку после `WaitNamedPipe`, общий срок ожидания, немедленный отказ при отсутствии службы/доступа и запрет повторного исполнения команды при потере ответа.

После нагрузки выполняется `Update.ps1` поверх тестовой установки: проверяются резервная копия БД, восстановление служб, сохранение действующей сессии, повторный вход с прежним паролем, сохранение whitelist и выключенное состояние блокировок. Эта проверка переустанавливает текущую сборку; она не заменяет приёмку миграции с реальными данными рабочего сервера.

Для rc.3 добавлены unit-регрессии локализованного имени `СИСТЕМА`, разрешения имени через SID и отказа другим SID, неисправных задач и устаревшего heartbeat. Нативная проверка разрешает имя LocalSystem, полученное от самой Windows, и отдельно отвергает LocalService. CI использует английский Windows runner; русские имена покрываются моделированием ответа Windows API. Реально установленная служба должна пройти `independent_watchdog` через новую CLI-команду `preflight` до и после обновления. Диагностика IP/whitelist проверяется без активации защиты.

## Не выполнено в рамках разработки

В rc.4 NAT проверяется моделированием настоящего формата LSM UserData и WTS-ответов: публичный источник/частный клиентский адрес, прежний whitelist, переподключение и подтверждение, другой пользователь/домен, старые события, смена IP и Session ID. Нативные тесты проверяют реальный `WTSSessionInfoEx`, раскладку структуры Windows SDK и XPath к LSM. GitHub runner не создаёт реальное RDP-подключение через внешний NAT; этот сценарий требует проверки на целевой системе.

Контролируемые реальные попытки RDP с отдельного внешнего IP, влияние на Kaspersky/SQL/1С, фактический throughput 1000 Windows-событий/минуту и end-to-end latency ≤5 секунд на целевом сервере, а также работа watchdog при реальной потере RDP. Эти пункты требуют отдельной [приёмки](ACCEPTANCE.md) с резервным доступом и разрешением владельца сервера.
